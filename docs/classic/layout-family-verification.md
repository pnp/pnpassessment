## Migration and regression audit

All upgrade `Up` operations were reviewed: `ClassicAssetPurpose` adds three columns, `ClassicPublishingLayoutReference` adds three and `ClassicPublishingLayoutTypeEvidence` adds ten. Tests assert all **16 operations are AddColumn**, generate upgrade SQL from both baseline levels, and reject DROP, RENAME, UPDATE and DELETE. The type-evidence migration is appended after the ContentType-based migrations; those historical migration files are unchanged. Defaults are version 0/null catalog, null declaration/resolved identity/observation JSON, None origin, Unknown statuses/decision and NotEvaluated reason. The generated Down methods remove their own added columns; these are not upgrade operations. No new migration is needed for this verification change.

The historical fixture deliberately preserves obsolete values, even a PublishingPage with Page Layout ContentType, rather than treating migration as a repair. Finalization may add the existing coverage Summary row; it does not rewrite the historical physical rows or six result tables. Restart is tested on finished historical results with a separately queued web, not as a promise to retain transient analysis from an interrupted, incomplete web. Existing interrupted-web cleanup behavior is unchanged.

The combined test diff was reviewed against the prior ContentType-based revision. The only prior public test-method name no longer present is `Layout_content_type_not_location_proves_an_asset`, explicitly replaced by `Own_type_not_content_type_or_location_proves_an_asset`. There are no added skips, conditional exclusions or disabled tests. The detailed [admission replacement audit](layout-routing-regressions.md) and [reference replacement audit](layout-reference-regressions.md) account for the other changed assertions:

- Positive purpose/exclusion/reference fixtures now require version 1 and source proof, while preserving identity, metadata, casing, sparse-update and failure assertions.
- Metadata-only confirmation reasons become `ConfirmedPublishingLayoutFamily`; unavailable-purpose selections now report the source/ancestry failure instead. Catalog uncertainty retains its metadata reason as one of multiple explicit reasons, rather than requiring that to be the sole reason.
- Confirmed members' metadata-request count changes from one to zero because type inspection must precede admission. Non-members and uncertain files still exercise metadata loading and eligible content-page behavior.
- Native historical CSV comparison now includes ContentTypeId, strengthening rather than removing the round-trip check.
- In this verification change, existing test bodies are untouched. The shared metadata fixture permits replacing its seed row with the actual discovery database row, and the historical test class is partial so the new tests reuse its column-snapshot helpers.

Five downstream accounting documents now explicitly say source-confirmed PublishingLayoutPage family under version 1, avoiding the earlier ambiguous phrase "Page Layout assets". The discovery/classicpages contracts correctly distinguish ContentType, source inference, runtime observation, purpose, acquisition status and historical authority.

## Limitations and review disposition

No remaining substantive implementation defect was reproduced in this offline scope. No live tenant, HTTP serialization or observed runtime handler was validated. The supported binder is intentionally conservative: fully assembly-qualified simple types, fixed root/System.Object anchors and operator-supplied deployment metadata; unsupported dynamic compilation, incomplete ancestry and unsupported binding features remain Unknown. Deployment correspondence of supplied assemblies is not runtime attestation. These limitations are explicit in [discovery.csv](csv-discovery.md), not silently converted to success.

The pnpcore worktree remained clean at `1f07296b186698c3cc9ca8580f00af36c0f3f4f5` (1.18.0). Reviewed source, tests, comments and public documentation use English, inherited xUnit/FluentAssertions/EF/CSV conventions, and synthetic fixtures; no private tenant data, credentials, internal task identities or private links were added. Existing deliveries/history were not rewritten. Final acceptance and any upstream publishing remain separate human decisions; this verification neither accepts nor publishes the change.
